# Companion Mode, Multiple Phones: Plan

_ADLC phase 2 (Plan). This is the **how** for the approved [`spec.md`](spec.md). `AC-1xx` refers to its criteria, `AC-n` (n < 100) to [v1](../spec.md)._

Status: **approved** · 2026-11-08. Rewritten for the owner's single-engine decision, revised after an independent review, then settled: the owner accepted N1–N11 with their defaults, and chose a **manual takeover** for M3 (N11 b)

## Owner decision this plan is built on

Card ids are renumbered whenever a game state is loaded: a state names cards by `Id:` only to link attachments inside the load (`forge-game/.../GameState.java:1390-1392`), and the loaded cards get new ids. So two phones running their own engines can't share card identity. **There is one engine, on the host.** Joined phones are views of the host's game. There's no mirror engine, no pen, no hand-over and no snapshot loss when a phone acts. When a joined phone acts (M2), the action runs on the host's engine, and any prompt it raises opens on that phone, which answers it with the host's card ids.

## 0. What exists, and why it shapes this plan

### 0.1 v1 Companion (this branch)
- **One real game, one GUI.** `CompanionMatch.start` registers every seat with the same `IGuiGame` (`CompanionMatch.java:26-34`). `HostedMatch.startGame` gives each human controller that GUI, an `FControlGameEventHandler`, and one `openView` per GUI (`HostedMatch.java:219-244`, `:262-264`).
- **Ops run on the game loop thread.** `CompanionTable.submit` queues an op and ends the priority prompt (`CompanionTable.java:595-607`). The controller runs the queue in `chooseSpellAbilityToPlay` (`CompanionPlayerController.java:40-82`). Every op that runs is logged and sets `ranSinceSave` (`CompanionTable.java:920-967`).
- **Steps and log.** A step is saved only at a settled point, a main phase with an empty stack (`CompanionTable.java:987-993`, `save` `:1160`). Steps go in `states/<n>.txt` (`CompanionStore.java:29-35`). Undo applies step n−1 in place, `discardAfter`, and appends an `UNDO` entry (`CompanionTable.java:692-751`). The log only describes what happened and can't be replayed. `appendLog` renumbers from a `lastSeq` cache (`CompanionStore.java:60`, `:284-305`). It takes the seq **even when the write fails** (`:289-291`) and swallows the failure (`:301-303`), so a failed write leaves a gap in the log's seqs. `loadState` isn't a pure read: it writes a settle `UNDO` for entries whose step isn't on disk (`:131-143`), and `CompanionTable.latestState` calls it (`CompanionTable.java:643-646`). `loadFinalState` reads without writing (`CompanionStore.java:161-164`). Only `writeWhole` fsyncs (`:398-410`).
- **A load renumbers cards** (above) and resets the life-this-turn tallies and commander stats (`CompanionGameState.java:114-119`, `:148-152`).
- **Some ops are lambdas.** Ready creatures (`CompanionMatchExtension.java:180`) and set life (`LifeDialog.java:90-98`, which calls `table.confirm` inside the op) can't travel. `AddCard`, `Reassign` and `Move` are records (`CompanionTable.java:93`, `:144`, `:175`), and `Move` already names its card by id.
- **The match screen hooks.** `MatchController.setExtension` is static and set before the match starts (`CompanionSetupScreen.java:342`). The game menu, the life tap and the card menu ask `getGameMenuExtension()`, which is non-null only when `isSingleOperator()` (`MatchController.java:893-912`; `VGameMenu.java:30-31`, `VPlayerPanel.java:1673`, `VCardDisplayArea.java:839`). The prompt bar's action button uses `getExtension()` with no such check (`MatchScreen.java:133-136`). Ctrl+Z calls `getGameController().undoLastAction()` directly (`MatchScreen.java:897-899`).

### 0.2 Forge net play already does "host runs the engine, remote renders a GameView"
- **`ProtocolGuiGame`** turns `IGuiGame` calls into `ProtocolMethod` events and keeps the peer's `GameView` current through a per-consumer `DeltaSyncManager` (`ProtocolGuiGame.java:36-52`). It knows nothing about transport: it takes an `IRemote` (`IRemote.java:6-10`), "an embedding host can consume them in process" (`ProtocolGuiGame.java:39-41`). It sends a full state on `openView` (`:289-295`) and on a checksum resync (`:220-226`, `:249-252`). It sends one on `GameEventSnapshotRestored(false)` **only once `objectsRegistered` is set** (`:546-549`), and that flag is set only by a batch that contains `GameEventGameStarted` (`:531-541`). A proxy attached after the game started never sees that event, so it never resends after an undo, and every flush takes the events-only path (`:560-565`), whose first `collectDeltas` sends the whole graph again right after the full state. While paused, `sendAndWait` returns null without sending (`:166-169`).
- **`RemoteClientGuiGame`** adds the Netty transport: events are wrapped for Java serialization, and the codec follows the game's tracker (`RemoteClientGuiGame.java:23-56`). **`RemoteClient`** holds the channel and a `ReplyPool`, encodes on the calling thread (`RemoteClient.java:70-92`) and blocks in `sendAndWait` (`:88-152`). The encoder substitutes IdRefs only for objects that consumer has been told about (`:185-197`), so each peer's bytes are its own and can't be shared. It can swap channels on reconnect (`:50-54`). `ReplyPool.get` waits without a timeout (`ReplyPool.java:31-41`).
- **Who flushes.** An input ending calls `InputQueue.removeInput` → `updateObservers` (`InputQueue.java:56-65`) from whatever thread ended it (`InputSyncronizedBase.java:44-55`, "thread irrelevant"), often the render thread on a tap. The forwarder's flush then walks the view while the game thread may be changing it, including each `TrackableObject`'s `consumers` `HashMap` (`TrackableObject.java:115-122`, `:179-184`). With one remote client this is rare; with eight it isn't.
- **Synchronized inputs block the game thread.** A target, attack or OK prompt parks the game thread in `awaitInput` (`InputSyncronizedBase.java:22-31`, `IGuiGame.java:327-329`) until the input ends. Nothing queued for the game thread runs meanwhile.
- **Wire:** `CompatibleObjectEncoder` = 4-byte length + LZ4 + Java serialization with tracker IdRefs (`CompatibleObjectEncoder.java:16-24`, `:77-119`). `CompatibleObjectDecoder` caps frame and decompressed size (`CompatibleObjectDecoder.java:25-47`). `WireClassFilter` allows only `forge.`, `java.util.`, Guava collections and a few `java.lang` types (`WireClassFilter.java:33-50`). It's package-private, but every decoder stream applies it (`:16-23`).
- **`GameEventForwarder`** batches events and flushes them at priority, at end of turn, and whenever an observed input queue changes (`GameEventForwarder.java:14-30`, `:41-75`). So a remote view gets what happened **before** the game thread blocks for input, the stack and combat steps included.
- **A hidden spectator already exists: `ReplaySession`.** It attaches a `ProtocolGuiGame` (`RecordingGuiGame`) to a local game the way `HostedMatch` wires a remote client: `setGameView`, `setForwarder`, subscribe the forwarder, observe every human's input queue, `setReplayGui`, `openView` (`ReplaySession.java:83-97`). It's the template for the **wiring** of Companion's remote views, but not for the timing: it attaches before the game starts (`HostedMatch.java:260`, before `match.startGame` at `:300`), so it does get `GameEventGameStarted`. Companion's phones attach mid-game, which needs `attachMidGame` (2.1). It's off for more than one human (`:52-57`), so a Companion game is never recorded.
- **The client.** `FGameClient` builds the pipeline (encoder, decoder, idle handler, `GameClientHandler`) (`FGameClient.java:99-125`), sends `LoginEvent` with the build version on connect (`GameClientHandler.java:231-245`), keeps a client tracker for IdRefs (`:93-152`), and reconnects with backoff 1, 5, 15, 45, 60 s, then gives up (`FGameClient.java:55`, `:329-397`). `ReplayClient extends FGameClient` is a precedent for a subclass (`ReplayClient.java:14`). `NetGameController` sends the screen's actions to the host and carries no seat (`NetGameController.java:26-110`).
- **The server.** `FServerManager` is a singleton (`FServerManager.java:82`, `:214-219`) tied to `ServerGameLobby`: a login takes a lobby slot (`:1089-1178`), a reconnect resumes by user name (`:1100-1131`, `resumeAndResync` `:929-972`), and a timeout converts the seat to AI (`:974-1016`). It only **warns** on a version mismatch (`:1161-1174`). `GameServerHandler` is package-private and calls `FServerManager.getInstance()` (`GameServerHandler.java:12-14`). Starting it sets `HostingServer` (`FServerManager.java:281`), which makes every match subscribe a network log listener (`HostedMatch.java:185-187`) and arms AFK timeouts (`HostingServer.java:37-40`). **No remote spectators**: every connection is a lobby slot.
- **Disconnect mid-prompt.** On `channelInactive` the server cancels every pending reply with null (`FServerManager.java:1239-1250`, `ReplyPool.java:47-55`). **A null is not a safe answer** for most dialogs. Only `showConfirmDialog`, `showOptionDialog` and `confirm` turn null into their default (`ProtocolGuiGame.java:404-424`). `getChoices`, `order`, `chooseEntitiesForEffect`, `manipulateCardList` (`:427-453`), `assignCombatDamage` and `assignGenericAmount` (`:384-391`) hand the null to the engine. Net play's own comment says `cancelAll` is safe only because its AFK path can only have `getAbilityToPlay` pending (`FServerManager.java:403-409`). On resume it re-shows the current input through `getInputQueue().updateObservers()` (`FServerManager.java:961-969`).

## 1. Approach

```
 host phone                                                          joined phone (Forge app)
 ┌──────────────────────────────────────────┐   Netty, LZ4 + Java    ┌──────────────────────────────┐
 │ HostedMatch ─ real Game ─ CompanionTable │   serialization        │ CompanionClient              │
 │   every seat's GUI: FloorGuiGame → host  │                        │  (extends FGameClient)       │
 │   screen, or the floor holder's proxy    │ ── view: setGameView,  │   GameClientHandler          │
 │ CompanionShareHost (own small server)    │    openView, applyDelta│   └► MatchController         │
 │   per phone: CompanionPeer               │    (and M2 prompts) ─► │      + CompanionViewExtension│
 │     = RemoteClient + RemoteClientGuiGame │ ── data: log lines,    │ CompanionStore (verbatim     │
 │     + GameEventForwarder                 │    step files, setup,  │   copy: data, never loaded)  │
 │   journal ◄─ CompanionStore hook         │    roster, end ──────► │                              │
 │   op queue = CompanionTable.submit       │ ◄─ hello, claim; M2:   │                              │
 │                                          │    op, answers, undo   │                              │
 └──────────────────────────────────────────┘                        └──────────────────────────────┘
```

Key decisions:

1. **Reuse net play's view stack; don't write a JSON protocol.** The view is the hard part: a live `GameView` with deltas, the stack and combat as they happen, IdRefs, checksums, resync, and prompts that block for an answer. Net play has all of that, in production on desktop and mobile. A JSON protocol would have to re-describe `GameView`, or ship snapshots (which renumber, so they can't carry M2 prompts), and would need its own prompt forwarding. The costs of reuse:
   - The wire is Java serialization of Forge classes, so both phones must encode the view the same way, checked by a protocol fingerprint (N1). Lambdas and records also cross between a desktop JVM and Android's runtime (a dev host with a phone joiner); slice 0 tests that both ways.
   - A later browser listener (spec §6.1) can't read it. It would need a second, JSON view endpoint on the same server, fed from the same `ProtocolGuiGame` hooks (`encodeEvents`, `onDeltaSent`). Nothing here blocks that, but nothing here builds it either.
   - The class filter allows lambdas (`SerializedLambda`, `WireClassFilter.java:44-50`), the same exposure net play accepts. B1 already says anyone with the code can join. Unlike net play, a connection that doesn't know the share token gets nothing deserialized: `TokenGate` checks a raw preamble first (3.1, **built in slice 00**).
2. **Our own small server, not `FServerManager`.** The singleton is a lobby with slots, AI takeover and AFK timers, and starting it flips `HostingServer` for every match (0.2). Companion needs spectators without a limit, seat claims, read-only phones, kick, and its own data stream. `CompanionShareHost` builds its own `ServerBootstrap` from the **public** pieces: `CompatibleObjectEncoder`/`Decoder` (and through them `WireClassFilter`), `IdleStateHandler` + `HeartbeatEvent`, `RemoteClient`, `RemoteClientGuiGame`, `GameProtocolHandler`. It never calls `HostingServer.set`, so no other mode changes. Net play's lobby, `LoginEvent` slot logic, draft, UPnP and chat are bypassed.
3. **Each joined phone is a spectator-style view on the host's `HostedMatch`**, wired like `ReplaySession` wires its hidden GUI (0.2), but attached **mid-game** through `attachMidGame` (2.1), on the game loop thread, at join and at every new game (a resume or restart makes a new `Game`).
4. **Joined phones store the host's log and step files as data**, byte for byte, through the v1 store. They never load them while following, and never call `loadState`, which writes (0.1). They're for the history (AC-105/107), for a restart (AC-112), and for M3, where the new host loads the latest step into its own fresh engine. Renumbering is harmless then, because it's again the only engine.
5. **M2: actions are ops on the host's queue, and prompts follow "the floor".** A joined phone sends a Companion op as data. The host runs it through `CompanionTable.submit` in arrival order (AC-118). While it runs, and until the table settles again, the phone that acted **has the floor**. Every seat's GUI is one `FloorGuiGame` for the whole match, which sends each call to whoever holds the floor, so targets, modes, "may" and OK all open on that phone, with the host's card ids (4.2). Moving the floor is a write to that delegate, not a GUI swap on the seats, so it works while the game thread is blocked in a prompt.
6. **M3 is a manual takeover (N11).** A term number on each log entry lets a returning old host or a stale follower see that it's behind; its unshared entries are cut and listed (AC-125). No freshness check, no catch-up from peers, no tie-breaking (4.3).
7. **Control is not log.** Seat claims, read-only and removal are host session state, sent as a roster. Attribution goes on each log entry (`by`, `byName`).

### 2.2 New code: `forge-gui`, package `forge.gamemodes.companion.share`

- `QrScanActivity` reuses the Camera2 controller and its YUV frames (`forge/app/camera/FrameAnalyser.java`), with ZXing's `QRCodeReader` on the Y plane.
- **Wi-Fi binding.** On a Wi-Fi network with no internet (a bare router, or the host's hotspot), Android keeps cellular as the default, and a socket to the host's LAN address leaves over cellular. While joined, `holdLocalNetwork(true)` finds the Wi-Fi `Network` (not a VPN) and keeps it with `requestNetwork` for `TRANSPORT_WIFI` without `INTERNET` (needs `CHANGE_NETWORK_STATE`, a normal permission), so Android doesn't drop a Wi-Fi without internet. - **Foreground service (Q27).** Android 12+ freezes a backgrounded app, which would stop the host serving. While sharing, a foreground service with a notification ("Sharing a Companion game") runs through `keepServing(true)`. **Joined phones run none, in every milestone** (N11): a follower only dials out, and it reconnects (and, in M3, searches for a new host) when it comes back to the foreground. The service was only needed for the dropped freshness check. A phone that takes over (M3) is a host, so it starts the service then.
- **Service by API level.** Minimum is API 26 (Android 8.0), target 35 (`src/main/AndroidManifest.xml:5-7`). Rules: from API 26 the service is started with `startForegroundService` and must call `startForeground` within about 5 s; the `FOREGROUND_SERVICE` permission is enforced from API 28 (already declared); the `android:foregroundServiceType` attribute and the three-argument `startForeground(id, notification, type)` exist from API 29; the type `specialUse`, its permission `FOREGROUND_SERVICE_SPECIAL_USE` and the `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property exist from **API 34**, where an app targeting 34+ must declare a type for every foreground service; from API 31 a foreground service can't be started from the background (it starts on the "Share game…" tap, in the foreground); `POST_NOTIFICATIONS` is a runtime permission from API 33 only, and below that the notification shows without asking. So the manifest declares `foregroundServiceType="specialUse"` (older platforms don't enforce it), and the code calls `startForeground(id, notification, FOREGROUND_SERVICE_TYPE_SPECIAL_USE)` only when `SDK_INT >= 34`, and the plain `startForeground(id, notification)` below that. `androidx.core` is excluded from the build (`forge-gui-android/pom.xml`, Sentry exclusions), so there is no `ServiceCompat`: two `SDK_INT` branches, checked on the oldest device to hand.
- **Permissions.** Already declared: `INTERNET`, `ACCESS_NETWORK_STATE` (`src/main/AndroidManifest.xml:27-28`) and `FOREGROUND_SERVICE` (`:25`). - **Local network permission (Android 17).** Android's local network protection blocks TCP connections to and from local-network addresses, outgoing and incoming, unless the app holds the runtime permission `ACCESS_LOCAL_NETWORK` (permission group `NEARBY_DEVICES`). It's enforced only for apps that **target API 37** (Android 17) or higher. Below that, `INTERNET` grants it implicitly, and the docs say not to declare or request it. Forge targets 35 (`:7`), so nothing changes today. ## 3. Transport and protocol

### 3.1 Wire
Net play's framing as is: 4-byte length, LZ4, Java serialization (0.2), heartbeat through `IdleStateHandler` and `HeartbeatEvent` (the server's 45 s reader idle, `FServerManager.java:76`, `:257`; the client writes every 15 s, `FGameClient.java:53-54`). Companion lowers the reader idle to 15 s on both sides, so AC-111's "disconnected" shows quickly.

**Token before deserialization (built in slice 00, Gate B fixes).** Before net play's `LoginEvent`, the client writes a raw, unserialized 8-byte preamble: `"FCMP"` + the share token from the code. Both writes happen in `channelActive` on the event loop, so the preamble is first on the wire. On the host, `TokenGate` (2.2) reads it before net play's `CompatibleObjectDecoder` sees any byte: a wrong magic or token, or no preamble within 15 s, closes the connection and counts in `refusedAtGate()`; a match removes the gate and passes the rest on. `hello` still carries and checks the token. `CompanionShareEndToEndTest` covers it: a client with the wrong token is closed at the gate, never welcomed, and the peer count doesn't change. Net play's own server is unchanged. One port per host: **36744** by default (net play uses 36743, `ForgeNetPreferences.java:28`), or the next free one up to 36753. The code carries the port.

### 3.2 View stream (from net play, unchanged)
- **Join:** attach (2.2) → `setGameView` → `openView(all seats)` → full state (`ProtocolGuiGame.java:258-266`, `:289-295`) → `attachMidGame` registers the phone for deltas (2.1). The client keys its tracker on the first `setGameView` (`GameClientHandler.java:95-117`).
- **Epoch.** The view epoch counts the host's full sends to that phone's game view: each undo, resume, new game, fresh attach and **checksum resync** (`ProtocolGuiGame.java:220-226`). After each full send, the host sends `epoch` on the data stream to that phone, so the phone always knows which board its card ids belong to. On `epoch` the phone also clears the client tracker's old card views (`resetTracker`, 2.1).
- **Live (AC-106):** the forwarder flushes a delta plus events at each priority, each end of turn, and each input-queue change (0.2). Companion's ops end the priority prompt and prompt again (`CompanionPlayerController.java:57-62`), so each op reaches the phones at once. **The stack, triggers waiting for OK, an engine combat and attacks or blocks being declared all show as they happen.** AC-106 is **not** narrowed.
- **Undo, resume, takeover:** a full state, through `GameEventSnapshotRestored` (2.1), which reaches a phone attached mid-game only because `attachMidGame` set `objectsRegistered` (0.2). A new `Game` (restart from the match screen, a resume) gets a fresh attach from the match's start hook. That's the same path as net play's next game in a match, with a new tracker per game (`ProtocolGuiGame.java:277-287`).
- **Safety net:** sampled checksums and `requestResync` (`DeltaSyncManager.java:47-53`, `:583-602`), handled by our server handler (2.1).

### 3.3 Data stream (Companion events)
**J** joined phone, **H** host.

| Dir | Event | Content |
|---|---|---|
| J→H | preamble (raw bytes, not serialized) | `"FCMP"` + share token, checked by `TokenGate` before anything is deserialized (3.1) |
| J→H | `LoginEvent` (net play's) | name, build version |
| J→H | `hello` | `fingerprint` (the protocol fingerprint, N1), `device`, `token`, `game` (null on first join), `have` = {`seq`, `term` (number, host device) of its last entry}, `terms` (M3: where each term starts in its log, a short list), its own addresses and takeover port (for the roster), and (M3) the newest host it knows of, with that host's term and addresses |
| H→J | `refuse` | reason + the host's build string and which part of the fingerprint differs (AC-110). The host shows a notice too |
| H→J | `welcome` | game id, host device, term, `setup`, `roster`, latest `seq`, latest `step`, step index `{n: sha256}`, and (M3) where the phone's log diverged |
| J→H | `claim` | a seat name, or null to watch |
| J→H | `want` | step numbers missing or with a different hash |
| H→J | `entries` / `step` / `setup` / `roster` / `end` / `removed` | verbatim log lines; `n`, sha256, text; as named |
| H→J | `gap` | a seq the host used up without writing an entry (a failed write, 2.1). The phone writes a tombstone for it |
| H→J | `epoch` | the view epoch, sent after every full view send (3.2) |
| J→H (M2) | `op` | an op from `CompanionOps` with its view epoch. `Undo` carries `expectedSeq`, the latest entry the phone saw |
| J→H (M2) | `away` / `back` | the phone left the app or came back (N9) |
| H→J (M2) | `op-result`, `status` | an op's result or notice for the phone that sent it; what `RemoteTable` reads |
| J→H (M3) | `taking-over` | the taker's new term, addresses and port, sent to the old host if it's reachable (4.3) |
| H→J (M3) | `new-host` | the new host's term, addresses, port and code, relayed by an old host to its phones, or sent by any host that learns it's behind (4.3) |
| H→J (M3) | `behind` | sent by a host to a phone whose `hello` shows a higher term: "this host is behind; follow the newer one" (4.3) |

**Order on join:** preamble (`TokenGate`) → login → `hello` → `welcome` → `claim` → catch-up (data) → attach (view). History rows appear as their entries arrive.

**Catch-up rule.** After `welcome`, the phone cuts back what the host lacks: entries past the last seq both logs share (`truncateLogAfter`, found from `terms`; this only happens after a takeover, to the old host or a follower that saw more of it than the taker, M3) and steps past the host's latest (`discardAfter(hostLatest)`). Then it compares the step index with its own hashes and sends `want`, naming steps it lacks **and steps whose hash differs**. The host sends the wanted steps first, then the entries after `have.seq`, or after the shared seq when the phone cut back (with `gap` for any missing seq). Steps first means a phone cut off halfway never holds entries that point at a step it doesn't have. An `UNDO` entry applied in order runs `discardAfter(entry.step)`, as on the host. The hash comparison catches the rest.

**Journal.** The store hook feeds the host's journal in write order: an entry when appended (or `gap` when the append failed), a step when saved, setup when changed, `end` last. Each session sends in that order. A joined phone writes each message to its store (`appendVerbatim`, `writeStep`) and never applies it to anything. It never runs `loadState` on that store, so it never writes a settle `UNDO` of its own (0.1): its log stays byte for byte the host's.

### 3.4 Join code, threads, lifecycle
- **Typed code:** Crockford base32 of the IPv4 address (4 bytes), port (2) and a random share token (4) = 16 characters, `XXXX-XXXX-XXXX-XXXX`. **QR:** `forge-companion:<code>?g=<game id>&a=<other addresses>`. A scanner tries every address in parallel. The dialog names interfaces ("Hotspot", "Wi-Fi"), because a hotspot address may be randomised per session. The token lasts for the game and is kept in `share.json` (B3: a removed phone may rejoin).
- **Threads.** Netty callbacks never touch the game or the UI. Attach, detach and resync go through `CompanionTable.runSystem` (game loop thread: `sync*` needs it, `ProtocolGuiGame.java:49-51`). Floor changes don't: they're a `volatile` write to `FloorGuiGame` from any thread, then `updateObservers()` (4.2), so they work while the game thread is blocked in a prompt. The forwarder's view flushes, and so each peer's encoding, happen on the game thread (2.1, `GameEventForwarder`; net play's reconnect handshake is the exception). Store writes run on one share executor per side. UI changes go through `FThreads.invokeInEdtLater`. The client side is net play's: deltas are applied on the GUI thread in order (`GameClientHandler.java:61-76`).
- **Attach waits for a priority prompt.** `runSystem` runs from `chooseSpellAbilityToPlay`. While the host sits in a target or choice prompt, a join completes once it's answered. Accepted: seconds at most.
- Screen kept on while sharing or joined (`preventSystemSleep`, `IDeviceAdapter.java:27`, Android `src/forge/app/Main.java:870`).

## 4. Behaviour by milestone

### 4.1 M1: follow along
- **Sharing (AC-101, 114):** "Share game…" starts `CompanionShareHost` and the service, writes `share.json`, installs the store hook and shows the code. With no phone connected, the hook only feeds the in-memory journal, so logging is exactly v1. The journal is rebuilt from the store on demand.
- **Joining (AC-102–105):** `JoinGameScreen` → login → `hello` → `welcome` (or `refuse`) → seat or Watch (`claim`). A taken seat is refused. The host's Me seat is the host's. Spectators are unlimited (the admission limit is set well above 6 + spectators, as net play's 64 is, `FServerManager.java:95-97`). There's no hard cap, but the host is measured only up to about 12 consumers (slice 01): past the **measured safe number** the host's share dialog shows a warning ("More phones than tested: the table may slow down") and still admits them (slice 05). Then catch-up, then attach. The phone's game folder uses the **host's game id**.
- **One active game per phone (Q29):** a phone with its own unfinished game is asked to end it first (`CompanionStore.loadActive`, `:352`).
- **Viewing (AC-106–108):** Forge's own `MatchScreen` with the host's `GameView`: board, zone tabs, stack, combat, card zoom, the command zone with the commander and table effect (`CompanionCards.java:80-95`). Placeholders show as card backs, because the hidden image key is on the card state the view carries (`CompanionCards.java:35-38`, `:60-63`). Known cards in hand show, as on the host. Own seat at the bottom and highlighted (N2). History and its player filter come from the phone's own copy of the log (`CompanionHistoryScreen` takes a list). **Nothing acts** (AC-108): the extension offers no acting item, and `PeerGate` drops every inbound screen call, so tapping a card, OK, Ctrl+Z, Concede or Offer Draw do nothing on the host.
- **Phones (AC-109):** roster with seat and connection; Remove sends `removed`, detaches, closes, and frees the seat (B5). The removed phone keeps its copy as an ended game (Q29) and may rejoin (B3).
- **Connection loss (AC-111):** the last view stays on screen with net play's reconnect banner. `CompanionClient` retries without end. On reconnect: login, `hello(have)`, catch-up, a **fresh attach** (full state), so no delta baseline is assumed. The host detaches a dropped phone at once rather than parking it as `FServerManager` does, because a view-only phone has nothing to resume.
- **Persistence (AC-112):** the data is on disk before anything is shown. A restarted joined phone reconnects from `share.json`. If the host can't be reached, it shows the last step as text (`CompanionSnapshotSummary`, as past games do, `CompanionPastGamesScreen.java:64-79`, read with `loadFinalState`, which writes nothing) and the history, and keeps retrying (N6). A restarted host resumes the game (v1), and sharing on the same port and token, so its phones come back by themselves.
- **End (AC-113):** `end` → `store.end(id)` → past games, read-only. A phone that missed it shows "Stop following" (Q29). An ended host keeps answering `end` until the app leaves Companion.

### 4.2 M2: act together
**Ops.** A seated phone that isn't read-only builds the same op the host's dialogs build, from its view (card ids are the host's), and sends `op` with the **view epoch** it was made against. The epoch counts the host's full resends (each undo, resume, new game). The host stamps the op with `origin`, `by` and `byName` and submits it (`CompanionTable.submit`), so it queues with the host's own actions in **arrival order** (AC-118). Nothing is merged or deduplicated. The epoch is checked **only for ops that carry card ids** (`Move`, `ReadyCreatures`): one made against an old epoch is refused ("the board changed: try again"), because a card id from before a load names nothing, or, after a resume, another card. Ops that name cards by name (`AddCard`, `Reassign`, `SetLife` and the switches) are never refused for their epoch (N10). The phone learns the current epoch from `epoch` after each full send (3.2), so a phone that was resynced by a checksum mismatch doesn't drift. `Undo` carries `expectedSeq`, and the host refuses it if another entry was logged since ("Something else happened first: check the history"), so two phones can't both confirm an undo and take back two actions. The host refuses ops from spectators and read-only phones (AC-121). With no connection the phone offers no action and keeps no queue (AC-117).

**The floor: whose screen prompts open on.**
- **One delegate, no GUI swapping.** Every seat's GUI is the same `FloorGuiGame` for the whole match (2.2). Seats' GUIs are never changed with `PlayerControllerHuman.setGui` (`PlayerControllerHuman.java:152-154`). Swapping them would have to happen on the game thread, and the game thread is parked in `awaitInput` during every target, attack or OK prompt (0.2), which is exactly when the floor must move on a disconnect.
- The floor is the host's operator by default. When an op from phone X **starts running** on the game loop thread, X takes the floor: the op sets `FloorGuiGame`'s holder to X's `RemoteClientGuiGame`. The seats are already registered on X's proxy (2.2), so `setCurrentPlayer`, `updateButtons` and `showPromptMessage` for any seat are accepted (`AbstractGuiGame.java:92-101`). An op from the host's operator takes the floor back the same way.
- While X has the floor, everything the engine asks opens on X: the cast's targets and modes, "may" and choices (dialogs through `sendAndWait`), the priority prompt with OK and End Turn for the stack, attackers in an engine combat, and the table's own `confirm` (the life dialog's "real gain or loss?"). X's screen sends its taps through `NetGameController`. `PeerGate` hands them to the controller of the seat whose input is current, because only one seat has an input at a time. The prompts are net play's own, so a target is picked on X's board by the host's card id.
- The floor returns to the host at the next **settled prompt**: the active seat's priority prompt in a main phase with an empty stack, nothing parked and no End Turn yield. That's the point where `atPrompt` saves a step (`CompanionPlayerController.java:71-76`). Later prompts from the stack go to the phone with the floor (N7).
- **Moving the floor** is a `volatile` write to the holder, from any thread, followed by `getInputQueue().updateObservers()` on the current seat, which re-shows the current input on the new holder, as `FServerManager` does on resume (`:961-969`). It doesn't wait for the game thread, so it works in the middle of a prompt. The old holder is told it lost the floor (an empty prompt and disabled buttons), and its selection highlight is cleared (`setSelection` with nothing chosen). That matters because an input's `stop()` sends its final selection to whoever is the GUI **then** (`InputSyncronizedBase.java:44-46`), which after a move is the new holder; without the clear, the old holder keeps a stale highlight.
- The event handler `HostedMatch` builds for the GUI uses the delegate too (`FControlGameEventHandler.java:43-46`). View updates go to the host's screen, so the host's board stays live, and its prompt bar says "Anna's phone is acting…". Prompt-like calls from events, such as `reveal` (`:260`), go to the holder, which is the phone whose action caused them. The game ends with the host's screen as the delegate's view target, so `endCurrentGame` closes the right screen (`HostedMatch.java:391-410`).
- **The host's own taps while X has the floor** are ignored by the controller (2.1). The operator's own actions join the queue and take the floor when they run.
- **"Take back the floor" (N8, M2-2).** The host's prompt bar shows it while a phone has the floor. It moves the floor to the host as above. If X has a dialog open, its pending reply is cancelled and the dialog is asked again on the host (below). There is no automatic timeout: `ReplyPool.get` waits without one (`ReplyPool.java:31-41`), and this button is how a stuck table gets going again. X is told "The host took back the floor".
- **Leaving the app (N9).** When the phone with the floor goes to the background, it sends `away`. If it hasn't sent `back` within about 10 s, the host treats it as disconnected for the floor (N4 below), but keeps its view connected.
- **Blocks (N3):** when the engine asks a defending seat to declare blockers, that one prompt opens on the defending seat's phone if it's connected and acting, else on the floor: `FloorGuiGame` sends that one input to the defender's proxy. Then the floor goes back to the holder. If the defender's phone drops or leaves the app, the block prompt moves to the host as in N4.
- **Actor disconnects mid-prompt (N4):** the host first moves the floor to itself, then cancels X's pending replies (`ReplyPool.cancelAll`, `ReplyPool.java:47-55`), and X's proxy is paused, so nothing more is sent (`ProtocolGuiGame.java:166-169`). A cancelled reply is **never handed to the engine**, because a null breaks most dialogs (0.2). `FloorGuiGame` sees that the call it forwarded came back while X no longer holds the floor, and asks the **same call again on the host's screen**, with the same arguments; the host's operator answers, and that answer goes to the engine. That covers `getChoices`, `order`, `assignCombatDamage`, `assignGenericAmount`, `manipulateCardList`, `chooseEntitiesForEffect`, `confirm` and the rest alike. A board prompt (targets, attackers, OK) is an input, not a reply, so the floor move's `updateObservers()` re-shows it on the host, and the operator finishes it. Net play does neither: it hands a timed-out seat to the AI and clears its inputs (`FServerManager.java:1004-1013`).
- **Results and notices** of X's op (`setOnResult`, `setOnNotice`, `CompanionSetupScreen.java:333-339`; the auto-add prompt, `CompanionMatchExtension.java:122-139`) go to X as `op-result`, not to the host's screen.

**Per action:** every v1 action is an op (AC-115): add by name or photo, capture and identification on the phone itself (only the card name travels), move, wrong player, set life (with `fire` answered through the floor's `confirm`), ready creatures, the combat and commander switches, End Turn and OK (`EndTurn`/`PassPriority` ops, or the phone's own prompt buttons when it has the floor), turn skip, and undo. "Auto-add photos" and "Keep photos" stay each phone's own preferences. **Default target (AC-116, B6):** the active seat on every phone, unchanged.

**Paid (v1's mana shortcut, branch `feature/companion-skip-payment`, under this stack).** On the host, a mana payment prompt relabels the prompt bar's action button "Paid", and a tap runs `CompanionTable.acceptManaAsPaid`, which calls `InputPayMana.acceptManaAsPaid` if that prompt is still open (`CompanionMatchExtension.runPromptAction`). In M2 a phone that **holds the floor** gets the same button on a payment prompt shown on its screen, and its tap is routed to the host like any floor input: it goes through `PeerGate` (only while that phone has the floor), and the host runs `acceptManaAsPaid` on the prompt that is current for that seat, on the host. The phone only needs to know that the current prompt is a payment prompt, which the host's `status` says. The other costs ({T}, a sacrifice, life) are paid as usual, through the floor. A tap after the prompt closed changes nothing, as on the host. The host's own Paid tap is ignored while a phone has the floor, like its other taps (2.1). Built in M2-2.

**Undo (AC-120):** the menu's Undo or Ctrl+Z on X. If the latest entry it would take back has a `by` other than X, X first shows "Logged by Anna's phone: Cast Lightning Bolt. Undo it?", from its own copy of the log. Then it sends `Undo(expectedSeq)` with the seq of the entry it showed, which is v1's undo on the host, refused if a newer entry was logged meanwhile (Ops above). Its full resend renumbers the board everywhere (2.1). Ctrl+Z's `undoLastAction` from a phone is routed to the same path by `PeerGate`, so it gets the confirmation too.

**Attribution (AC-119):** `by`/`byName` on every entry written while sharing. History shows "· Anna's phone".

### 4.3 M3: takeover (manual, N11)
From M1 on, the roster carries each seated phone's addresses and its **takeover port** (36744, or the next free one when it last checked), and `share.json` keeps them. Nothing listens on that port until the phone takes over.

1. **Start (AC-122):** "Take over as host" in the game menu of every seated phone, after a confirmation that says what's lost (N5) and, when the phone is disconnected, "Phones that saw later actions will lose them". It doesn't need the old host to be gone, and checks no other phone (spec §6 item 8).
2. **Stop following:** if connected, send `taking-over` (new term, addresses, port) to the old host, then close the client. It keeps its Wi-Fi binding, which is harmless for a host that only accepts connections. The store is left as it is: the verbatim copy, with `lastSeq` already past the last entry (`appendVerbatim`, 2.1).
3. **Become host (AC-123):** append a `HOST` entry (term = the highest term in its log + 1, host = this phone). Then start a **fresh engine from the latest step**: v1's resume path (`CompanionTable` + `CompanionMatch.start` + `startFromLatest`, `CompanionTable.java:654-664`), in host mode. Its card ids are new, which is fine: it's the only engine now. That path calls `loadState`, which writes a settle `UNDO` for entries past the latest step (0.1). That's the only write besides the `HOST` entry, and it's accepted: it lands after the `HOST` entry, in the new term, through the journal, so every phone that follows gets it, and the history then says what the board says (N5). This is the first `loadState` this store has ever had, so nothing else is written by surprise. Then `CompanionShareHost` starts on the takeover port (the next free one if taken), the foreground service starts (2.4), `share.json` becomes *hosting*, and `ShareDialog` shows the new join code.
4. **Old host still reachable (AC-124):** on `taking-over` with a higher term, the old host sends `new-host` to every phone it has, stops its match and server, and follows the new host itself, through step 6.
5. **Phones find the new host (AC-124):** a joined phone that loses its host (or gets `new-host`) runs `HostSearch`: every few seconds it dials the old host's addresses, the address in `new-host` if any, and every roster entry's addresses and takeover port, all in parallel. Only a host listens, so whatever answers `welcome` for this game id is a host. If its term is higher than the phone's, the phone follows it with no approval: catch-up (3.3, which cuts back what the new host lacks), fresh attach. If that fails, because the new host's port or address changed or the old host never shared the taker's address, the phone keeps the AC-111 banner and offers "Join by code", which uses the same path. A phone that reaches a host with a **lower** term gets `behind` plus the newer host's addresses from its own `hello`, and keeps searching.
6. **Former host returns (AC-125):** a restarted host resumes sharing (4.1), and while it has a roster it also runs `HostSearch` every 10 s for a host of this game with a higher term. It also learns it's behind from any phone's `hello` that names a higher term, which carries that host's addresses. Either way it stops its match and server, follows the new host, and catches up: `welcome` says where its log diverged (from `terms`). It keeps the dropped entries in memory, cuts back (`truncateLogAfter`, a whole rewrite through `writeWhole`), runs `discardAfter(host latest)`, reconciles steps, and shows its operator the dropped entries that changed the game, to log again.
7. **No peers (AC-127):** a phone that takes over with nobody connected is a host with no followers, exactly AC-114.
8. **Lost in a takeover (N5):** whatever the taker hadn't saved as a step. That's an unresolved stack or engine combat, parked ops and a turn skip, yields, `combatTurn` (`CompanionTable.java:223`), and, from the load itself, the life-this-turn tallies and commander damage (`CompanionGameState.java:114-119`, `:148-152`). Also anything the old host logged that the taker never received; if the old host comes back, step 6 lists it.
9. **Not handled (spec §6 item 8):** two phones taking over at once. Each becomes host with the same term number. They don't merge: a phone that meets an equal term from a different host device doesn't follow it automatically, and shows "Another phone is also hosting this game". The players pick one; the other's operator joins it by code, which is step 6.
10. **Hotspot host dies (Q29):** the network goes with it, so no phone can reach anyone. The takeover confirmation says so. Venue Wi-Fi survives.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Builds differ, so Java serialization breaks silently | Refuse unless the protocol fingerprint matches (N1). A build string can't do it: every dev build says `GIT` |
| A desktop JVM host and an Android joiner (or the reverse) serialize lambdas or records differently | Slice 0 sends the view and every travelling op both ways between a desktop dev instance and a phone |
| Companion's in-place load bypasses delta tracking | Fire `GameEventSnapshotRestored` (2.1). Checksums and resync remain the net (3.2) |
| A remote view of a placeholder, the table effect or a hidden hand renders oddly (no `PaperCard` for "Unknown card" on the client) | Slice 0 checks a placeholder in hand and library, the command zone and the commander on a joined instance |
| The floor moves while an input is shown | One delegate, a `volatile` holder, then `updateObservers()` re-shows the input; the old holder is cleared (4.2). Engine tests |
| A cancelled peer reply reaches the engine as null | Never: `FloorGuiGame` re-asks it on the host (N4). Engine tests for `getChoices` and `order` |
| A phone holding the floor stalls the table (thinking, backgrounded) | Visible on the host as "Anna's phone is acting…". "Take back the floor" (N8), the 10 s away grace (N9), and a disconnect (N4) all return it |
| Eight peers cost the host too much (each encodes its own bytes; a full resend after undo goes to all) | Flushes and encoding on the game thread only (2.1); measured in slice 0 on a real phone; if too slow, one sender executor from snapshots |
| More spectators than measured (the spec sets no limit, B4 targets 8 phones) | Slice 01 also measures about 12 consumers on a real host phone, and records the safe number. Past it the host sees a warning, not a refusal (4.1, slice 05) |
| A failed log write on the host stops every phone's log | The used-up seq travels as a tombstone (`gap`, 2.1) |
| Attach waits for the host's open prompt | Accepted (3.4) |
| Venue Wi-Fi isolates clients | Clear error pointing to the host's hotspot |
| Android routes over cellular on a Wi-Fi with no internet | Process binding (2.4), checked on real phones in slice 0 |
| Android 12+ freezes a backgrounded host | Foreground service (Q27) |
| Android's local network protection blocks LAN sockets for apps targeting API 37+ (Android 17), unless `ACCESS_LOCAL_NETWORK` ("Nearby devices") is granted. A blocked connect looks like a timeout | Not active while Forge targets 35 (`INTERNET` grants it implicitly). Slice 01 checks hosting and joining on the newest Android phone to hand, and whether the hotspot case counts as local network. When the target moves to 37: declare the permission, ask on Share and Join, and name the permission in the error (2.4) |
| Hotspot address randomised, several interfaces | Every address in the QR; interfaces named; parallel tries |
| Host address changes mid-game | Retry stored addresses; else scan again (same token) |
| Host is the hotspot and dies | No takeover possible; said plainly (Q29) |
| A big join (hundreds of 10 KB steps) | Steps by hash, so a rejoin sends only new ones; LZ4 per frame. Measured in slice 0 |
| Card database fingerprint differs between desktop dev and phone builds of one release | Checked in M1-3; fall back to hashing the names the game uses |
| Takeover loses the old host's live state | N5; same limits as v1 resume |
| The taker missed the old host's last actions (manual takeover, no freshness check) | Accepted (N11 b). The confirmation warns when the taker is disconnected; if the old host returns, its extra entries are listed (AC-125); otherwise they're gone |
| Two phones take over at once | Not settled automatically (spec §6 item 8): each shows "another phone is also hosting", and one operator joins the other by code (4.3 step 9) |
| A follower can't find the new host (port taken, address changed, never in the roster) | Falls back to joining by code (AC-124) |
| Minimum Android is API 26 (8.0), but `specialUse` exists only from API 34 | `SDK_INT` branch: typed `startForeground` on 34+, plain foreground service below (2.4). Checked on the oldest device to hand |
| An old tablet as a joined phone runs out of memory | A joined phone runs the full Forge app with the card database in memory, so RAM, not the API level, is the likely limit (spectators need no service, so API 26 is fine). Optional phone check in M1-3 |
| A later browser listener can't read the wire | Needs a separate JSON endpoint (decision 1) |
| An attacker on the LAN | Out of scope (B1). The token prevents wrong joins, and `TokenGate` checks it **before anything is deserialized** (3.1, built in slice 00), so Java deserialization only ever sees bytes from a phone that has the code. After that, net play's class filter and size caps |
| iOS | Untouched; typed code only |
