# Slice 00: Walking skeleton, dev build

**Branch:** `feature/companion-multi-00-skeleton`, from `feature/companion-multi`. **Plan item:** section 9, slice 0, Oracle 1 (Oracles 2 and 3 and the measurement are slice 01).
**Depends on:** v1 slice 08 landed on `feature/companion-multi` (spec 7: the v1 action types must be stable). No earlier multi slice.
**Proves:** host shares → a second instance joins **after the game started** → it gets the full board → host actions show live → a host undo (which renumbers every card) shows too.

## Result
On the dev build, the operator starts a Companion game with 3 players and adds a card. They open the game menu, pick "Share game…", and see a 16-character code. A second dev instance, with its own user folder, opens Companion → "Join game", types the code and sees the same board: every seat, hands as card backs, the command zone. The host adds Gray Merchant of Asphodel; the joined board shows it, and the life changes, within a second. The host undoes; the joined board goes back too. Nothing the joined instance taps changes the host's game.

## Design for this slice
Plan sections 1, 2.1, 2.2, 3.1, 3.2, 3.4. One engine, on the host; the joined instance is a net-play view of the host's `HostedMatch` (plan "Owner decision").

### Changes to existing code (`forge-gui`)
- **`CompanionGameState.applyNow`:** fire `GameEventSnapshotRestored(true)` before the apply and `(false)` after it. Today a Companion load fires neither (only `GameSnapshot.java:68-70` and `UndoManager` do). With them, each remote proxy sends a full state (`ProtocolGuiGame.java:546-549`) and the host's own screen rebuilds through `onSnapshotRestored` (`FControlGameEventHandler.java:56-59`, `:320-330`; mobile `MatchController.java:468`). Needed because undo and resume renumber every card (`GameState.java:1390-1392`): deltas over old ids would name nothing.
- **`ProtocolGuiGame.attachMidGame()`**, public, called on the game thread: `sendFullState()`, then `syncManager.registerNewObjects(gameView)` and set `objectsRegistered`. Without it a proxy attached after the game started never sees `GameEventGameStarted` (`:531-541`), so it never resends after an undo (`:546-549`), and its first flush sends the whole graph a second time (`:560-565`). Registering after the full send makes the delta baseline exactly what the phone has.
- **`CompanionTable.runSystem(Runnable)`:** run on the game loop thread before the op queue, **not logged, no `ranSinceSave`** (unlike `runOne`, `CompanionTable.java:920-967`). Runs only from `chooseSpellAbilityToPlay` (`CompanionPlayerController.java:40-82`), so it never runs while a target or choice prompt blocks the game thread; an attach waits for the next priority prompt (plan 3.4, accepted). Wake the loop the way `submit` does (`CompanionTable.java:595-607`).
- **`FGameClient`:** one protected hook, additive: an extra inbound handler before `GameClientHandler` in the fixed pipeline (`FGameClient.java:110-118`), for Companion's data messages. Nothing else in `FGameClient` changes in this slice.

### New code (`forge-gui`, package `forge.gamemodes.companion.share`)
Messages are small `NetEvent` classes (strings, ints, lists) in a `forge.` package, so `WireClassFilter` takes them (`WireClassFilter.java:33-50`) and ProGuard keeps them (`proguard.cfg:74`). Give each an explicit `serialVersionUID`.
- **`CompanionShareHost`:** its own `ServerBootstrap` from net play's **public** pieces: `CompatibleObjectEncoder`/`Decoder` (`CompatibleObjectEncoder.java:16-24`, `CompatibleObjectDecoder.java:25-47`), `IdleStateHandler` + `HeartbeatEvent` with a **15 s** reader idle (plan 3.1), `RemoteClient`, `RemoteClientGuiGame`, and a public `GameProtocolHandler` subclass (nested is fine) that also handles `requestResync` as `GameServerHandler.beforeCall` does (`GameServerHandler.java:41-53`). Port **36744**, or the next free one up to 36753 (net play uses 36743, `ForgeNetPreferences.java:28`). It **never** calls `HostingServer.set` (`FServerManager.java:281`), so no other mode changes, and it doesn't use `FServerManager`. Admission: inherited `LoginEvent`, then `hello` with the right token → `welcome`, then attach. **No version check** in this slice (07 adds it). Everyone is a spectator. Netty callbacks never touch the game or the UI (plan 3.4).
- **`CompanionPeer`:** one joined instance: a `RemoteClient` + `RemoteClientGuiGame` + `GameEventForwarder`. **Attach**, on the game thread through `runSystem`: `setGameView(null)` then `setGameView(game.getView())`, `setForwarder`, subscribe the forwarder, `addObserver` on every seat's input queue, `setOriginalGameController(seatView, gate)` for **every seat**, then `openView(all seats)`, as `ReplaySession.attach` does (`ReplaySession.java:83-97`) plus the seat registration; then `attachMidGame()`; then send `epoch`. **Detach** on disconnect and on the host leaving: remove the observers, `shutdownForwarder`. Every seat being local on the client means the client creates a `NetGameController` per seat (`FGameClient.java:268-277`), hands are visible as on the host (`AbstractGuiGame.java:260-271`), and the no-human overlay is never built.
- **`PeerGate`** (`IGameController`): what the host invokes for a peer's inbound screen calls. Drops everything (`concede`, `drawOfferAction`, `undoLastAction` included) and answers any request with null, as `GameProtocolHandler` does for a missing controller (`GameProtocolHandler.java:62-74`). This is all of AC-108 on the host side.
- **`CompanionClient extends FGameClient`:** login is the inherited `LoginEvent` (`GameClientHandler.java:231-245`); then `hello`; receives `welcome` and `epoch` through the extra inbound handler. The view goes through the inherited `GameClientHandler` to `MatchController.instance` (`GuiMobile.java:356-359`); the client keys its tracker on the first `setGameView` (`GameClientHandler.java:95-117`). Reconnect stays net play's for now (04 changes it).
- **Messages** (one file of nested classes, or one per message): `hello` {token, game = null}, `welcome` {game id}, `epoch` {n}. The epoch counts the host's full sends to that peer (fresh attach, undo, checksum resync `ProtocolGuiGame.java:220-226`), sent on the data stream after each one (plan 3.2). Nothing reads it yet besides a log line; 04 and M2-1 use it.
- **`JoinCode`** (record): Crockford base32 of IPv4 (4 bytes) + port (2) + random share token (4) = 16 characters, `XXXX-XXXX-XXXX-XXXX` (plan 3.4). Token random per share in this slice (kept across restarts from 04).
- **`LocalAddresses`:** usable IPv4 addresses (site-local, up, not loopback, cellular or VPN) by walking `NetworkInterface.getNetworkInterfaces()` itself. Don't reuse `FServerManager.getAllLocalAddresses` (`:645`): it starts with `getLocalAddress`, which routes towards 8.8.8.8 (`:647`, `:631`) and fails without internet. Raw interface names here; friendly names in 09.

## Results
Chunk 1 (engine), by `CompanionLateAttachTest` (in-process `ProtocolGuiGame` on a recording `IRemote`, 3 seats, setup state plus two cards):
1. **`attachMidGame` baseline: corrected.** As designed (`sendFullState()` then `registerNewObjects`) the first flush after the attach still carried the whole graph: 614 new objects, 8,107 bytes, against a full state of 8,977 bytes. `registerNewObjects` only starts dirty tracking and deliberately leaves each object to go again, in full, in the next delta (`DeltaSyncManager.walkAndRegister`). `attachMidGame` now runs one `collectDeltas` walk and drops its packet (it registers every object as sent and clears its dirty bits), then `sendFullState()` with the walk's sequence number. First flush after: 2 new objects, 3 changed, 1,501 bytes. No change to `DeltaSyncManager`.
   - The attach as described (`setGameView(null)`, `setGameView(view)`, `openView`, `attachMidGame`) sends the full state **4 times** (the fallback in `setGameView`, the fallback and `sendFullState` in `openView`, then `attachMidGame`'s). Correct, but 01's measurement should count it.
   - Net play's own undo resend (`ProtocolGuiGame.handleGameEvents`) sends the full state, then a delta whose new objects are the whole renumbered graph again, for the same reason. Unchanged here (net play mustn't change); worth the same fix later if 01 finds the undo resend too big.
2. **v1 regression: engine unchanged, host screen to be checked by hand.** `TableEditorTest` (183) and forge-gui's companion tests, `CompanionStoreShould` included, are green unchanged. What the events now do on the host's screen: `FControlGameEventHandler` queues a refresh of every player's life, mana and zones (a redraw), and mobile's `onSnapshotRestored` clears card animation state (`VCardDisplayArea.CardAreaPanel.resetForUndo`). **One audible change:** `EventVisualizer` mutes sounds between the two events and plays the "rewind" sound at the end, so a Companion undo, and also every game start and resume (`startFromLatest` goes through `applyNow`), now plays the rewind sound when sound is on, and the load's own sounds are muted. Check on the dev build; if the sound at start is unwanted, `startFromLatest` can skip the events (no view is attached before the game starts in this slice; 04's fresh attach sends its own full state).

Chunk 2 (host side: `CompanionShareHost`, `CompanionPeer`, `PeerGate`, `ShareMessages`, `JoinCode`, `LocalAddresses`):
1. **The attach sends one full state, not four.** `ProtocolGuiGame.attachMidGame(GameView, seats)` replaces `setGameView(null)`, `setGameView(view)`, `openView`, `attachMidGame()`: it binds the view without a send (`AbstractGuiGame.setGameView` through `super`) and binds the codec tracker, walks once (chunk 1's baseline), `sendFullState()`, then sends `openView` bare, without the fallback and full sends `ProtocolGuiGame.openView` adds. Wire on join: `welcome` → `setGameView` (full, with the walk's sequence number) → `openView(all seats)` → `epoch 1`. The view comes before `openView`, as on net play's reconnect (`FServerManager.resumeAndResync`), since the client keys its tracker on the first `setGameView`. Net play's `setGameView`, `openView` and `sendFullState` are unchanged; the no-arg `attachMidGame()` is gone (only chunk 1's test used it). `CompanionLateAttachTest` now asserts the peer gets exactly `[setGameView, openView]` on attach.
   - **But `openView` is nearly a second board.** The encoder never turns `setGameView` or `openView` args into IdRefs (`CompatibleObjectEncoder.shouldReplaceTrackables`), so `openView` with every seat carries every `PlayerView` inline, zones included: 8,383 bytes for the `setGameView`, 8,131 for the `openView` (serialised, before LZ4; 3 seats, setup plus a card). So a join costs about two boards, down from about five. 01's measurement should count both. Making `openView` lighter would change net play's wire, so it isn't done here.
2. **Admission, as built.** Pipeline: net play's encoder (no byte tracker) and decoder (same 9,766 KiB frame limit), `IdleStateHandler` with a 15 s reader idle, the admission handler, then a `GameProtocolHandler` subclass. The admission handler answers `HeartbeatEvent`, takes the first `LoginEvent` (name cut to 64 printable characters, `libgdx` flag kept), then `hello`: right token → `welcome` → attach queued with `runSystem`. A wrong token, a `hello` before login or a second `hello` closes the connection (no refusal message before 07). A connection not admitted within 15 s is closed. Before admission everything else is dropped; after it only `GuiGameEvent` and `ReplyEvent` go on to the protocol handler, whose controller is the peer's `PeerGate`. The host never sends a `LobbyUpdateEvent`; chunk 3's check 3 is whether `FGameClient` needs one.
3. **Port and addresses.** Binds on all interfaces (Wi-Fi binding is 01), 36744 or the next free one up to 36753; a taken port is detected from the bind future and the next is tried. No `SO_REUSEADDR` (on Windows it lets a second host bind the same port). `LocalAddresses` keeps site-local IPv4 on interfaces that are up and not loopback, point-to-point or virtual, and drops names starting with `rmnet`, `ccmni`, `pdp`, `wwan`, `clat`, `v4-` (cellular), `tun`, `ppp`, `wg`, `ipsec`, `utun`, `tailscale`, `zt` (VPN), `docker`, `veth`, `br-`, `virbr`, `vboxnet`, `vmnet` (desktop bridges). On this WSL box: one code, `eth0`.
4. **Detach.** `CompanionPeer.close()` (connection gone, or `CompanionShareHost.stop()`) pauses the proxy at once, so nothing more is sent, takes the forwarder off every seat's input queue, cancels pending replies, and queues `shutdownForwarder` with `runSystem`. `Game` has no unsubscribe, so the forwarder stays on the game's event bus until the game ends and the paused proxy drops what it gets, as `CompanionTable`'s own engine log copier does.
5. **Epoch.** The proxy (`CompanionPeer.PeerGuiGame`, a `RemoteClientGuiGame`) sends `epoch n` after every full state it sends: 1 after the attach's `openView`, then one after each undo, resume or checksum resync. `requestResync` from the phone is marked on the proxy before the call reaches `PeerGate`, as `GameServerHandler.beforeCall` does.
6. **Small changes to existing code:** `CompanionTable.seats()` (public, read-only: the peer attaches to every seat's input queue) and `RemoteClient.getReplyPool()` made public (plan 2.1). `FServerManager` is untouched.
7. **For M2:** `PeerGate.getYieldController()` returns null. That's safe in M1, because a peer's proxy is never a seat's GUI, but once `FloorGuiGame` sends prompts to a peer's proxy, `AbstractGuiGame.currentYieldMessage` would call it on the gate. M2-1 must give the gate a yield controller, or forward to the seat's.
8. **Smoke check, not in CI.** A scratch localhost test, run once and then deleted, drove a real `CompanionShareHost` over a raw Netty client: port fallback (a second share took the next port), heartbeat echoed, a wrong token closed, `welcome` with the table id, then `[setGameView, openView, epoch 1]` after the loop ran the system ops, `concede` and `undoLastAction` from the phone changed nothing, and the peer count went to 0 on disconnect. Chunk 3's end-to-end test should cover the same ground with the real `CompanionClient`.
9. **For chunk 4:** the API is `new CompanionShareHost(table)`, `start()` (returns the port; `IllegalStateException` when none of 36744 to 36753 is free), `codes()` (a list of `Code(interfaceName, JoinCode)`), `peerCount()`, `stop()`. `JoinCode.parse(typed)` returns an `Optional`, accepts lower case, spaces, dashes, and I/L/O read as 1/1/0; `text()` gives `XXXX-XXXX-XXXX-XXXX`. The code has no check character: a mistyped code that still parses just fails to connect. On mobile, the panels fill their zones through `updateZone` calls, not from the view at `openView`. Net play's reconnect has the same shape and works, but if the joined board shows empty zones (check 4), look there first.

Chunk 3 (client side: the `FGameClient` hooks, `CompanionClient`), by `CompanionShareEndToEndTest` (forge-gui-desktop, real localhost socket: a host table with 3 `CompanionPlayerController` seats shares through `CompanionShareHost`; a `CompanionClient` on a `HeadlessNetworkGuiGame` joins by its `JoinCode` after a card was added; the test thread plays the host's game loop):
1. **Check 3, login flow: no lobby update needed.** `GameClientHandler.beforeCall` takes `setGameView` (creates and binds the tracker) and `openView` (`setNetGame`, then `setGameControllers`) with no lobby state at all; `LobbyUpdateHandler` only passes them on. `openView` with every seat also sets `seated` (`FGameClient.setGameControllers`), so net play's reconnect already applies to a joined client: no `markSeated` hook was needed, and none was added.
2. **`FGameClient` hooks, all additive (net play's defaults unchanged):** `newExtraInboundHandler()` (null by default; a new one per connection, so a reconnect gets one, put after `LobbyUpdateHandler` and just before `GameClientHandler`), and **`readerIdleSeconds()` / `heartbeatIntervalSeconds()`** (default 45 / 15, as before). The last two weren't in this bundle's design ("one hook"), but are needed: the host's reader idle is 15 s (chunk 2) and net play's client heartbeats every 15 s, so a joined client with nothing to send raced the host's idle close. `CompanionClient`: heartbeat 5 s, reader idle 15 s (plan 3.1). No backoff hook: reconnect stays net play's (5 tries, 1 to 60 s) until 04.
3. **`CompanionClient(username, gui, JoinCode)`**: its handler's `channelActive` lets `GameClientHandler` write the `LoginEvent` first, then writes `hello{token, null}`, on every connection (so a net-play reconnect says hello again and gets a fresh attach). It takes `welcome` (`welcomedTo()`) and `epoch` (`epoch()`) off the stream and logs them; everything else goes on to net play's handler and so to `gui`. Wire seen: login, hello → welcome → `setGameView` → `openView` → epoch 1 → deltas; undo → full `setGameView` → epoch 2.
4. **What the test proves:** the joined board (every player's life, and the card ids in every zone) equals the host's after the join, after an action (a delta; epoch stays 1), after a host undo that renumbered every card (epoch 2), and after an action following the undo (deltas resolve against the new ids). The client has a controller for every seat. `concede` and `undoLastAction` from the client, then a `getActivateDescription` question (answered null by `PeerGate`, its `CardView` arg resolved through the codec tracker the attach binds) change nothing: no op queued, no one lost, the board and the epoch as they were.
5. **`CompanionShareHost.codeAt(Inet4Address)`** (new, public): the code for one address, e.g. loopback. The test needs it (CI may have no site-local address, so `codes()` can be empty), and the dev-build oracle (two instances on one PC) can use it too.
6. **For chunk 4:**
   - `connect()` is net play's: synchronous, and a refused connection comes out of it as an exception (Netty rethrows the `ConnectException` unchecked). Call it off the UI thread and catch everything around it.
   - A wrong token, or a host gone, shows as the connection closing: since the client isn't seated yet, `FGameClient` doesn't retry and calls each lobby listener's `close()`. So `JoinGameScreen` can register an `ILobbyListener` (`addLobbyListener`) to learn of a failed join; `welcomedTo()` tells "wrong code/token" (null) from "host left after welcome".
   - The view goes to the `IGuiGame` given to the constructor: on mobile pass `GuiBase.getInterface().getNewGuiGame()` (`MatchController.instance`, reset for a new match), after setting `CompanionViewExtension`. `MatchController.openView` builds the `MatchScreen` and opens it itself (`Forge.openScreen(view)`), so the screen appears on `openView`. It calls `DiceOverlay.getInstance().attach(getGameView().getGame())`: on a client the view has no `Game`, as in net play, which already goes through there.
   - Leaving: `client.close()` (no reconnect after it).
