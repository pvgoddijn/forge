# Slice 01: Skeleton on real phones

**Branch:** `feature/companion-multi-01-phones`, stacked on `feature/companion-multi-00-skeleton`. **Plan item:** section 9, slice 0, Oracles 2 and 3 and the measurement.
**Depends on:** 00 (`CompanionShareHost`, `CompanionPeer`, `PeerGate`, `CompanionClient`, `JoinCode`, `LocalAddresses`, `ShareDialog`, `JoinGameScreen`, `CompanionViewExtension`, `attachMidGame`, `runSystem`, the snapshot events).
**Proves:** the skeleton works where it will be used: Netty listening on an Android phone, a joiner on a Wi-Fi with no internet while mobile data is on, desktop and Android exchanging the view both ways, and a host phone serving 8 viewers, then about 12 to find the safe number for the spectator warning (05).

## Result
The owner hosts a Companion game on one Android phone and joins it from a second Android phone by typing the code, on a router with no internet (or the host's hotspot), with mobile data **on** on both. The joined phone shows the board, follows a card being added, and follows an undo. A desktop dev instance can join a phone's game, and a phone can join a dev instance's game. With 8 viewers attached, the host phone still feels the same to its operator, and the joined phone still updates within a second. A second run with about 12 viewers says how far past 8 the host can go.

## Acceptance criteria
Delivered in part:
- **AC-102** WHEN a user picks "Join game" in Companion and scans the QR code or types the join code THE SYSTEM SHALL connect to that shared game over the local network, without internet. _Here: typed code, two real Android phones, no internet, mobile data on. Scan: 08. Full phone check: 09._
- **AC-106** WHEN the host's game changes THE SYSTEM SHALL show the change on every connected phone within 1 s on the same local network. _Here: measured on a real host phone with 8 consumers (spec B4). Stopwatch check on several phones: 09._

## Design for this slice
Plan 2.1 (`GameEventForwarder`, `IDeviceAdapter`), 2.4 (Wi-Fi binding, local network permission), 3.1 (`TokenGate`, built in 00), Risks ("desktop JVM and Android", "eight peers", "more spectators than measured", "Android routes over cellular", "local network protection").

### `forge-gui`
- **`GameEventForwarder`:** a flush asked for from any thread but the game thread only **marks a flush as due**; the game thread does it at its next flush point (the next priority, input or end of turn). Today an input ending calls `InputQueue.removeInput` → `updateObservers` (`InputQueue.java:56-65`) from whatever thread ended it (`InputSyncronizedBase.java:44-55`), often the render thread on a tap, and the flush then walks the view while the game thread may be changing it, including each `TrackableObject`'s `consumers` `HashMap` (`TrackableObject.java:115-122`, `:179-184`). After this change the view is walked, and each peer's bytes encoded, on the game thread only. Net play keeps working: its flushes off the game thread become a short delay. **Measure that the delay can't be felt** (below).
- **Fallback, only if the measurement says so:** encoding moves to one sender executor working from a per-peer snapshot taken on the game thread (plan 2.1). Decide from the numbers and record the decision here.
- **`IDeviceAdapter`** (`forge/interfaces/IDeviceAdapter.java:27-60`): `holdLocalNetwork(boolean)`, default no-op, and `openLocalNetworkSocket()`, default null (the default route). _(Gate B: was `bindToLocalNetwork(boolean)`, a process binding; see Results 9.)_
- **`CompanionClient`:** `holdLocalNetwork(true)` before connecting, `false` on leaving; each connection's socket from `openLocalNetworkSocket()` through a new `FGameClient.channelFactory()` hook.
- **`CompanionPeer`** (or the host): timing and size logging for the measurement: per flush, time on the game thread for all peers and bytes per peer; the size of each full state. Behind a debug flag or plain `netLog` lines; no UI.

### `forge-gui-android`
- **`Main.java`** (`forge-gui-android/src/forge/app/Main.java`): `holdLocalNetwork(true)` finds the Wi-Fi `Network` and keeps it with `requestNetwork` for `TRANSPORT_WIFI`; `openLocalNetworkSocket()` binds a new `SocketChannel` to it with `Network.bindSocket`. Only the join's sockets are bound (plan 2.4). _(Gate B: was `bindProcessToNetwork`, which also sent card image downloads and DNS to the Wi-Fi with no internet.)_ A host that is the hotspot only accepts connections and needs no binding.
- Manifest: `CHANGE_NETWORK_STATE` added (Gate B; a normal permission, granted at install, for `requestNetwork`). `INTERNET` and `ACCESS_NETWORK_STATE` were already declared. Netty 4.1.115 (`forge-gui/pom.xml:50-54`) and LZ4 are already in the APK; ProGuard keeps `forge.**` and `net.jpountz.**` (`proguard.cfg:74`, `:100`).

### Measurement harness (not production, not CI)
To reach 8 consumers with two phones: a small `main` in `forge-gui-desktop` test sources (for example `forge.gamemodes.companion.share.ViewerLoad`) that opens N headless joins to a given code, reusing `HeadlessNetworkClient`. **Not a JUnit test**, so CI never runs it (`CONTRIBUTING.md:85`). The real joined phone plus 7 headless viewers = 8 consumers on the host phone; plus 11 = about 12. The headless viewers write the `TokenGate` preamble like `CompanionClient` does (built in 00), or the host closes them at the gate.

## Results
Chunk A (`forge-gui`: the forwarder, the binding hook, the measurement logging). Phone checks and the harness are still to do.

1. **Game-thread-only flush, as built.** `GameEventForwarder.flush()` (and so `update()`, the input-queue observer) runs the flush only on the game thread. _(Gate B:)_ that is the thread recorded once: the one that delivers `GameEventGameStarted` (fired before the mulligans), or, failing that, the first priority or end of turn (only the game loop fires them), or the thread given to the constructor by a mid-game attach (`CompanionPeer.attachNow`, on the game loop). The first version also took any `ThreadUtil.isGameThread()` thread, which matches net play's "Game BT n" answer threads and "Game AI Eval", and whatever thread last delivered an event (the EDT fires some, `InputAttack.java:346`, `InputBlock.java:86`, `:168`), so two threads could encode at once. Until the game thread is known (before the game starts) a flush goes out where asked, as before slice 01. Anywhere else (the render thread or EDT ending an input with a tap, a Netty thread, a net play answer) it only marks a flush as due. The game thread does it at its next priority (even when only redraw hints came since the last batch, which normally sends nothing), its next input (`setInput` notifies the observers on the game thread) or the end of the turn. `isFlushDue()` is there for tests.
   - **Can a due flush be lost?** Not in the paths found. An input ended off the game thread is what wakes the game thread, and the game thread then reaches priority or a new input, where it flushes. The game thread also flushes before it blocks for an input, so while it's blocked the only events waiting are ones fired off the game thread. They wait until the game thread next runs, which is no later than they would have waited for any other flush. The last flushes, when nothing changes the view any more, use the new `flushNow()` (any thread): `ProtocolGuiGame.shutdownForwarder` (net play's `HostedMatch.endCurrentGame` calls it on the EDT, so `flush()` there would have dropped the batch) and `ReplaySession.finish`. `HostedMatch`'s end-of-game flush is already on the game thread.
   - **One flush at a time** _(Gate B)_: `receiveGameEvent`, `flushNow` and `hasPendingEvents` are `synchronized` on the forwarder, and `ProtocolGuiGame.updateGameView()` holds the same lock, so two threads never encode for one proxy at once and a batch is never split or sent twice. Recording the game thread alone wasn't enough: events also arrive on the EDT, and `flushNow` (the forwarder let go, a reconnect) runs off the game thread. Nothing called under the lock waits for another thread (the sends are Netty writes), so it can't deadlock; an event from the EDT waits at most for one flush's encoding.
   - **A due flush waits while the game thread is in a plain dialog** _(Gate B, MINOR-5)_: a `sendAndWait` question that isn't an input (a confirm, a choice list) blocks the game thread without ending an input, so a flush marked due meanwhile (events fired off the game thread, which is rare) goes out only after the answer. It doesn't affect what the dialog shows: `syncAndSendAndWait` sends the state the question needs first.
   - **Reconnect** _(Gate B, MAJOR-1)_: `FServerManager.resumeAndResync` (a Netty thread) calls `updateGameView()` and then `openView`. With events waiting, `updateGameView` flushed them and returned, and the flush, now only marked due off the game thread, sent nothing, so the client got `openView` before any game view. `ProtocolGuiGame`'s `flushPendingEvents` (used only by `updateGameView`, which the caller needs done before its next send) now calls `flushNow()`, as before slice 01. The same applies to a `syncAndSend` from an input's thread. So these two paths still walk the view off the game thread, as they always did, now under the forwarder's lock.
   - **Net play timing:** before, a flush asked for when an input ended on the EDT walked the view and encoded on the EDT straight away. Now it goes out when the game thread next reaches priority, an input or the end of the turn, which in practice follows at once, because ending the input is what releases the game thread. Net play's tests are green unchanged: `NetworkPlayIntegrationTest` (its 6 stress tests skip unless `-Drun.stress.tests=true`, as before), `ClientReconnectTest`, `DeltaSyncUnitTest`, `AbuseLimitsTest`, `LobbySlotAuthorizationTest`, `ProtocolGuiGameInProcessTest`, `ProtocolGuiGameSingleThreadTest`, `Wire*`, and `GameEventForwarderTest`.
   - **Not measured yet:** Check first 4 and dev-check step 1 (tap to joined board) need the UI. The fallback (a sender executor) stays undecided until those numbers are in.
2. **`IDeviceAdapter.holdLocalNetwork(boolean)`**, default no-op, and **`openLocalNetworkSocket()`**, default null (the default route). _(Gate B: replaced `bindToLocalNetwork(boolean)`; see 9.)_ Both may be called on any thread (the Netty event loop, net play's reconnect scheduler, the join thread, the UI thread). The client calls `holdLocalNetwork` with each value at most once in a row, but an implementation should still treat a repeat call as harmless. `JoinGameScreen` passes `Forge.getDeviceAdapter()` to `CompanionClient(username, gui, code, IDeviceAdapter)` (the 3-argument constructor means no adapter).
   - **When the client holds:** `true` at the start of every `connect()`, net play's reconnect attempts included, and again on a manual rejoin. `false`, once, on every way out: `close()` (Leave, leaving `JoinGameScreen`), also when it comes while a connect is under way; a first connect that fails (Netty rethrows a refused connect as an undeclared checked `ConnectException`, so this is a `finally`, not a `catch (RuntimeException)`); a connection that closes with no reconnect to follow (refused at the gate or the hello, the host gone before the game, the 30 s attach timeout); and the reconnect ending `FAILED` or `SEAT_LOST`, through a new `FGameClient.onReconnectStateChanged(state)` hook (protected, no-op by default, net play unchanged). The client keeps holding while it reconnects.
   - **Each connection's socket** comes from `openLocalNetworkSocket()`, through a new protected `FGameClient.channelFactory()` (default `NioSocketChannel::new`, so net play is unchanged): `CompanionClient` wraps the device's `SocketChannel` in a `NioSocketChannel`, or makes a plain one when the device returns null.
3. **Measurement logging**, off by default. Turn it on with `COMPANION_SHARE_MEASURE=true` in the host's `<userDir>/preferences/server.preferences` (net play's preferences file; on Android it's in the Forge user folder), or with `-Dforge.companion.measure=true` on a desktop JVM. When it's off, the host has no meter, the encoder has no byte tracker, and the code paths are the ones from before. When it's on, `netLog` (logcat on Android) writes these lines:
   - `[CompanionMeasure] flush #n: P peers, X ms on the game thread, bytes [name=b, …]`: for each flush point, the time all peers' sends took on the game thread (the delta walk and each peer's encoding), and the bytes each peer got. Bytes are the encoder's output: LZ4-compressed, with the 4-byte frame length. A flush is written when the next one starts, or when the share stops.
   - `[CompanionMeasure] full state to <name>: B bytes, X ms`: each full state (the attach, an undo, a resync).
   - An undo's flush includes its full state. A heartbeat answered during a flush adds a few bytes.
   - **Example**, from `CompanionShareEndToEndTest` with the measurement forced on for one local run (3 seats, a few cards, 1 peer, desktop JVM, so not a phone number): attach full state 9,138 B; a delta flush 1,861 B at 7.8 ms; the undo's flush 17,385 B at 17.7 ms (its full state was 9,251 B; the delta after it carries the renumbered graph again, as slice 00 noted).
   - The surefire `argLine` in the root pom overrides `-DargLine`, so the system property can't be passed through `mvn test`. Use the preference, or `java -D…` for `ViewerLoad` or the dev jar.

Chunk B (`forge-gui-android`, the harness, the APK).

5. **`Main.java`: only the join's sockets are bound** (Gate B; the first version bound the whole process, see 9).
   - `holdLocalNetwork(true)` looks up the Wi-Fi `Network` at once (`getAllNetworks`, the first with `TRANSPORT_WIFI` and not `TRANSPORT_VPN`, as a VPN over Wi-Fi reports both), so the connect that follows straight away already has it, and calls **`requestNetwork`** for `TRANSPORT_WIFI` **without** `NET_CAPABILITY_INTERNET` (a bare router has none; `NOT_VPN` is in the builder's defaults). The callback is kept only once `requestNetwork` returned. `onAvailable` records the network; `onLost` of the recorded one looks for another Wi-Fi, else none (the default route). `false` unregisters the request in a `try`/`finally` that always clears the state. All under one lock; a repeat call returns at once. A failure (a `SecurityException`, the per-app request limit) is logged and the join goes on with the network found at once.
   - `openLocalNetworkSocket()`: `SocketChannel.open()`, then `network.bindSocket(sc.socket())` (API 22). No Wi-Fi network, or the bind throws: the socket is closed and null is returned, so the join connects on the default route. Card image downloads, DNS and everything else in the app keep the default network (mobile data on a Wi-Fi without internet).
   - **`requestNetwork`, not `registerNetworkCallback`:** a registered callback only watches; a request is what makes Android keep a network that has no internet, instead of tearing it down as unneeded once mobile data is the default. It needs **`CHANGE_NETWORK_STATE`, now declared in the manifest** (a normal permission, granted at install, no prompt). A request for a Wi-Fi that isn't there waits; it doesn't turn Wi-Fi on.
   - **Released** on leaving (above) and in `Main.onDestroy`, so a request never outlives the activity.
   - **The phone is the hotspot:** its access point isn't a `Network` to `ConnectivityManager`, so no Wi-Fi is found, the socket isn't bound (logged as `No Wi-Fi network: connecting on the default route (this phone may be the hotspot)`), and the default routing reaches the hotspot's clients. A host never binds (only `CompanionClient` calls it). A phone joining **another** phone's hotspot is a Wi-Fi client, so it binds as on a router.
   - APIs: `NetworkRequest.Builder`, `requestNetwork`, `unregisterNetworkCallback`, `getAllNetworks`, `getNetworkCapabilities` (API 21), `Network.bindSocket(Socket)` (API 22). All within minSdk 26; no `androidx`.
   - Log lines (logcat, tag `NETWORK`): `[Companion] Holding the local network; Wi-Fi now: …`, `Bound the join's socket to Wi-Fi network …`, `Wi-Fi network … available`, `Wi-Fi network … lost; now: …`, `Let go of the local network`, and on failure `Couldn't bind the join's socket …` or `Couldn't request the Wi-Fi network …`.
   - **Not provable off a phone:** that `bindSocket` accepts the `SocketChannel`'s socket on ART (it reads the descriptor through the socket adaptor; if it throws, the log says `Couldn't bind the join's socket` and the join falls back to the default route, which on a no-internet Wi-Fi with mobile data on means a timeout), that the bound socket reaches the host with mobile data on, that a card image download still works while joined (it should go over mobile data), and that the Wi-Fi stays up with the request held. These are [Phone] step 4 below.

MINOR-8 (release on activity destroy), MINOR-9 (`onLost` looks for another Wi-Fi), MINOR-10 (skip `TRANSPORT_VPN`), MINOR-11 (callback kept only after a successful request; release in `finally`), MINOR-12 (`requestNetwork` + `CHANGE_NETWORK_STATE`): in 5.
   - **MINOR-6, `close()` during a connect:** the hold is still a state (the Wi-Fi request), so `connect()` lets go in its `finally` when `left` is set. Not tested: the window is between a reconnect attempt entering `connect()` and holding, and `close()` stops the reconnect scheduler, so there's no cheap way to land in it.
   - **MINOR-7, a late close of an older connection:** `DataHandler.channelInactive` acts only for the newest connection whose `channelActive` ran. Not `FGameClient.isActiveChannel` (left package-private): `connect()` sets that channel only after the connect returns, and a host closing at once (a wrong token) can beat it, which is the case this handler exists for (`CompanionShareEndToEndTest`'s wrong-token client would no longer be told).
   - **m6, a failed first connect kept the hold:** a real bug. Netty rethrows a refused connect as a checked `ConnectException` (`AnnotatedConnectException`) it doesn't declare, which the old `catch (RuntimeException)` missed, so a refused first connect stayed bound. Now a `finally`. Test `CompanionClientLocalNetworkTest.aFailedFirstConnectLetsGoOfTheLocalNetwork`: red with the old catch (`[true]`, no let-go), green after.
   - **Reconnect `FAILED` / `SEAT_LOST` lets go:** `CompanionClientLocalNetworkTest.theDevicesSocketConnectsAndAFailedReconnectLetsGo` connects to a plain local `ServerSocket`, checks that Netty connected the device's own `SocketChannel` (its local port is the one the host accepted) and that the hold stays through `RECONNECTING`, then calls the `onReconnectStateChanged` hook with `FAILED` and `SEAT_LOST`. It calls the hook directly: the real path to `FAILED` waits through net play's backoff (1+5+15+45+60 s), too slow for CI.
